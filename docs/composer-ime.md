# 输入法Enter保护

聊天输入框收到带`isComposing=true`或旧式`keyCode=229`信号的Enter时，交给浏览器继续处理选词，不调用发送，也不打开键盘快捷键弹窗。输入结束后的普通Enter继续发送，Shift+Enter换行，按钮或表单走原有发送流程；Ctrl/Meta+Enter不作为发送快捷键。

原模板把Enter与prevent绑定后直接调用sendMessage，另一条keydown还可打开斜线菜单。修复把判断移到现有textarea的composerEnter：输入法信号先返回，普通Enter才preventDefault并调用sendMessage。保留.exact，冗余斜线keydown移除，普通`/`由已有sendMessage处理同一菜单。未引入新的输入状态、服务器端点或持久化字段。

## 实际复现与验证

329564a先提交三项浏览器控制，原实现3/3失败，均阻止了输入法事件默认动作。原失败trace证实标准与229控制分别发出了1条真实消息POST，斜线控制未发送但打开了快捷键弹窗；不是仅凭代码推断。提取结果与trace指纹在composer-ime-validation.json，原日志保留。

修复后相同三项控制通过。每项实际创建项目并上传合成DOCX，生产Worker解析；标准和229事件均不触发消息请求、不清空草稿，整个保存版本不变。下一次普通Enter恰好产生一次实际发送，回答可查看来源，解析和报告保持，刷新保留已保存版本。斜线控制验证输入法不触发菜单、普通斜线Enter正常打开；Shift+Enter插入换行，Ctrl/Meta+Enter不发送，按钮最后只发出一次含原换行的问题。

另与已有草稿、就绪与停止流程组合运行共8项浏览器通过；完整生产构建272Node/90浏览器通过。新增0Node/3浏览器，外部模型请求0。没有修改服务端问答、SSE、草稿策略、解析和导出结构，原4000字符及解析就绪门槛保留。
