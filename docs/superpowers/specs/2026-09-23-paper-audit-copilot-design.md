# 期刊投稿预审 Copilot 项目设计文档

**文档状态：** 总体架构与《生态学报》适配评判标准建议稿；具体权重、规则样例与报告版式待确认  
**日期：** 2026-09-23  
**修订日期：** 2026-09-24  
**产品形态：** Web 端、匿名项目制、面向投稿作者  
**首个目标期刊：** 《生态学报》中文版（ISSN 1000-0933，官网 ecologica.cn）；其他期刊通过配置扩展  
**核心定位：** 为作者提供投稿前的专业同行评审视角、证据定位和修改建议，输出拒稿、大修、小修或录用的系统审稿建议，并支持可选分项评分；不代表期刊作出正式编辑决定。

## 1. 产品概述

本系统是一套面向投稿作者的论文预审 Copilot。作者在类似 Codex 的项目工作台中上传 PDF 或 Word 论文，通过持续对话发起解析、专业预审、问题解释和版本复查。系统在右侧工作区展示论文解析结果、带真实批注效果的论文原文以及完整评审报告。

系统的核心不是单次大提示词，也不是让通用智能体自由审稿，而是 Paper Audit Engine：

> 文档结构层 + 可替换的语义分析层 + 可配置评判方案 + 结构化评判结果 + 问题账本 + 独立报告模板

当前阶段确定模块职责、数据归属、接口和版本关系，并补充通用评判标准与报告内容建议（第 18、19 节）；具体期刊规则、权重和业务版式仍可配置。领域、方法、统计、证据、创新性和可复现性等评审模块按配置选择；多角色控辩审是可选策略。正式结果必须通过与其类型相适应的证据和规则校验，报告基于已保存的结果生成。

### 1.1 本轮架构决策边界

| 现在确定 | 保持可配置或后续确定 |
|---|---|
| 项目、论文版本、文件与解析产物管理；首个目标为《生态学报》 | 更细的研究类型、正式规则与后续期刊扩展 |
| 文档结构与语义分析分层、证据定位 | 主张提取方法、完整论点证据图的启用范围 |
| 后台任务、依赖调度、重试、追溯 | 评审模块数量、顺序与是否采用控辩审 |
| 评判结果与问题账本独立持久化 | 权重、评分尺度、严重程度及其映射 |
| 评判方案与报告模板分别版本化 | 报告章节、业务字段、版式及导出格式 |
| 对话工具边界、访问隔离和删除机制 | 模型、解析器、智能体运行时的具体选型 |

技术栈属于候选实施方案；本轮冻结逻辑职责，不要求把每个模块部署成独立服务。架构验证通过不代表专业评判能力已经验收。

## 2. 用户与目标

### 2.1 目标用户

- 准备向期刊投稿的论文作者；
- 需要在投稿前发现研究设计、论证、证据和表达问题的研究人员；
- 中文、英文以及中英混排论文作者。

### 2.2 核心用户目标

用户应当能够：

1. 上传 PDF 或 DOCX 论文并获得可靠解析；
2. 从专业审稿视角理解论文的优势、缺陷和可能受到的质疑；
3. 点击任何评审意见，定位到具体句子、段落、表格、公式或图；
4. 围绕论文和评审意见持续询问 Copilot；
5. 查看结构化的完整预审报告；
6. 上传修改版本，了解问题的解决、延续和新增情况；
7. 主动删除项目及其全部数据。
8. 获得拒稿、大修、小修或录用的总体建议及可追溯理由；关键材料不足时明确暂缓判定。
9. 判断论文是否符合目标期刊收录范围，并查看创新性等多维评价及可选分项得分。

### 2.3 成功标准

- 每条正式判断均包含可核验的证据；缺失类判断还需记录检查范围与解析覆盖情况；
- 聊天、论文批注和评审报告引用同一份评判结果与问题数据；
- 用户可以在两次点击内从评审意见定位到原文；
- 新版本能够区分已解决、仍存在、新增和需重新确认的问题；
- 系统明确区分事实、模型推断和无法判断的事项；
- 不输出未经校准的录用概率。

## 3. 产品原则

### 3.1 证据优先

正式判断必须关联证据。涉及原文陈述时引用具体位置；涉及“未报告某事项”时记录检索范围、最相关位置、附件覆盖和解析完整性，不把“未找到说明”推断为“作者没有执行”。没有足够证据的判断只能标记为探索性意见或无法判断，不能混入已验证结论。

### 3.2 Copilot 而非自动裁判

系统帮助作者发现风险、理解原因和确定修改方向，可以输出“建议拒稿、建议大修、建议小修、建议录用”。这些是基于当前材料和评判方案的系统审稿建议，不是期刊正式决定或录用概率预测。无法支持总体结论时使用“待补充材料／暂无法判定”的流程状态，不强迫四选一。

### 3.3 对话是入口，结构化对象是真实数据

上传、解析、评审、报告生成和版本更新都显示在聊天时间线中，但论文、解析与语义产物、评判方案、评审任务、评判结果、问题、证据和报告必须独立持久化，不能只存在于聊天文本中。

### 3.4 专业评审不是角色扮演

评审模块使用明确的输入、知识包、检查目标、输出结构和验证过程。不得仅依赖“你是一位资深专家”式提示词产生专业性。

### 3.5 可复现、可版本化、可校准

每次分析记录模型、规则包、提示词、解析器和评审模块版本。同一版本论文可以重放关键检查，并能够使用人工评审样本持续校准。

记录输入快照、参数和原始输出以支持审计；重放不承诺模型输出逐字一致。评判方案与报告模板独立版本化，历史产物不随配置更新而被覆盖。

### 3.6 评判结果与报告呈现解耦

评判引擎产出结构化结果，报告服务按模板选择、组织和呈现结果。同一批结果可以生成不同报告。仅调整布局、章节或措辞时不重新评审；模板要求的数据不存在时，明确显示缺失，或由用户发起补充检查。报告模型不得自行补造事实、评分或问题。

## 4. 首版范围

### 4.1 首版包含

- 匿名项目工作台；
- 项目创建、重命名和删除；
- PDF、DOCX 上传；
- 中文、英文和中英混排识别；
- 论文版本管理；
- 文档解析、章节识别和低置信度提示；
- 独立语义分析接口，按评判需求提取研究问题、方法、数据、结果、结论和贡献主张；
- 文档 Paper IR 与可扩展的语义关系记录；完整论点证据图按需建设；
- 可插拔的 Review Pack 框架；
- 后台评审任务、阶段进度、失败重试；
- 句子级或区域级论文批注；
- 结构化评判结果与问题账本；
- 目标期刊资料、收录范围匹配、四档总体建议及可选分项评分；
- 输入框旁的评判标准选择器、稿件类型确认与输出方式选择；首个标准为《生态学报》预审标准；
- 创新性分层评价：论文内部贡献论证，以及基于受控检索或用户提供材料的有限文献比较；
- 版本化报告模板、报告数据快照与在线展示；正式报告格式确定后接入；
- 基于论文与已验证意见的 Copilot 对话；
- 新旧版本问题对比；
- 用户主动删除全部项目数据。

### 4.2 首版明确不包含

- 用户注册、登录和跨设备同步；
- 查重率检测；
- 全量参考文献真实性核验（创新性比较中实际引用的外部来源仍须核验）；
- 自动改写或一键接受修改；
- 自动修改并导出新版 Word；
- 录用概率预测；
- 代表期刊作出接收或拒稿决定；
- 穷尽全部文献或保证成果“全球首次”的创新性结论。

### 4.3 评判标准的首版处理

第 18 节提供通用评判标准、四档建议逻辑和可选百分制草案，第 19 节提供报告内容建议。它们是本项目的设计提案，不是任何期刊已发布的正式规则。当前实现 Review Pack、评判方案、结果契约、报告模板接口、执行器和版本机制，不将草案分值默认宣传为期刊标准，也不把示例报告目录固化为数据库结构。

架构联调可以使用明确标记为“演示”的规则和模板验证数据流；演示输出不能作为专业评判能力的证明。论文内部的结构、逻辑、方法描述、结果证据和一致性检查，在对应规则确定并通过验证后逐项开放。缺少适用方案时显示“尚未配置评判标准”，不运行未定义的专业检查或生成伪精确分数。

正式规则接入前需定义适用条件、依据来源、所需输入、输出结构、例外、无法判断条件以及测试样例；评分和严重程度映射为可选配置。通用草案经确认和样例验证后可以发布为通用方案；目标期刊另有规则时显式覆盖并记录来源，不设计通用规则编程语言。

## 5. 信息架构

界面采用 Codex 式三栏工作台。

### 5.1 左侧：项目与版本

左侧只负责导航和管理：

- 新建项目；
- 项目列表；
- 当前项目的论文版本；
- 项目重命名；
- 项目设置；
- 删除项目。

项目默认以论文题目命名。没有解析出题目时使用文件名。一个项目对应一篇论文，可以包含多个修订版本。

项目设置允许选择目标期刊和稿件类型，或上传期刊征稿范围、作者指南和审稿表。未指定期刊时运行通用研究质量评审，期刊匹配标为未评估；不得虚构某期刊的偏好。

### 5.2 中间：持续对话与项目时间线

中间区域是主交互区，承担：

- 上传 PDF 或 DOCX；
- 用户与 Copilot 持续对话；
- 展示解析、评审、报告和版本事件；
- 发起专业预审；
- 打开右侧产物；
- 围绕具体批注追问。

聊天输入框同时是文件拖拽区域。项目没有论文时显示大型上传引导；已有论文后恢复为紧凑输入框，继续支持拖入新版本。

输入框旁显示当前“评判标准、稿件类型、输出方式”，为整个当前评审提供明确上下文；具体交互见第 5.4 节，不要求用户在每条消息中重复说明期刊。

### 5.3 右侧：上下文工作台

右侧不设置第二个聊天输入框，只负责展示当前工作对象。包含三个主要视图：

1. **论文解析**：展示 Compiler 进度、论文结构和研究模型；
2. **论文批注**：展示原文、红线标注和页边批注；
3. **评审报告**：展示完整专业预审报告。

用户可以手动切换，系统也根据中间聊天中的操作进行上下文切换。

### 5.4 评判标准选择与必要追问

采用“显式选择为主，缺失时询问”的交互，首版只提供《生态学报》预审标准，后续通过标准目录增加其他期刊。

```text
评判标准：[《生态学报》预审标准 ▾]
稿件类型：[自动识别，待确认 ▾]   输出方式：[文字意见 ▾]
┌──────────────────────────────────────┐
│ 拖入论文，或输入想重点检查的问题……     │
└──────────────────────────────────────┘
[上传论文]                    [开始评审]
```

输出方式默认“文字意见”，用户可切换为“文字意见＋评分”。评分方案未完成发布时该选项显示原因并不可用于正式评审。

- **标准选择：** 首版预选《生态学报》预审标准并清楚展示，无需再问用户是否选择同一个期刊。详情注明“依据公开要求整理的系统预审标准”，列出版本、适用类型和能力范围，不称为期刊官方审稿表。
- **稿件类型：** 解析后给出识别结果及依据，用户可修改。类型未确认或与已有选择冲突时，在启动评审前用一次简短确认解决；确定后不在每条消息中追问。
- **自然语言选择：** 用户说“按生态学报评”时同步更新选择器；提及另一期刊的文章不等于要求切换标准，语义不清时只询问这一点。
- **用户关注点：** “重点看创新性”等文字作为附加关注，不覆盖正式方案的必查项。用户明确只做局部检查时，记录为专项评审，不自动给完整总分或四档总体结论。
- **未支持标准：** 如用户要求首版尚未提供的期刊，明确显示尚未支持，不把《生态学报》规则改名冒充其他标准；允许保存用户提供的要求供后续配置。
- **临时追问：** 仅针对无法由材料确定且影响评判的信息，如研究类型、缺失附录或必要的采样说明。问题关联具体检查项，不要求用户回答与当前判断无关的信息。

选择器保存项目默认设置；同一项目的新论文版本继承该设置。首次运行时把解析出的确切标准版本保存为项目默认，后续升级显式选择。每次开始评审，把论文版本、标准版本、稿件类型、输出方式和附加关注保存到 ReviewRun。任务进行中更改选择器只影响下一次启动，不能改写正在执行的任务。

标准升级时显示更新提示，用户可选择保留旧版本以便比较，或使用新版本重评。旧报告始终保留原标准；同一论文换标准后生成新任务与新报告，不覆盖已有结果。涉及权限撤销或严重错误而停用的旧标准只允许查看历史，不继续启动。

首版仅开放已发布且通过基本验证的研究类型组合；草案仅用于有明显标记的预览和联调。界面可以预留综述等类型，但未完成适配时必须标为尚未支持，不能静默套用实证研究评分。

## 6. 核心用户流程

### 6.1 新建项目与上传

1. 用户点击“新建项目”；
2. 在中间聊天区拖入 PDF 或 DOCX；
3. 上传动作成为聊天时间线中的文件卡；
4. 右侧自动打开“论文解析”；
5. 系统开始解析并展示真实进度。

### 6.2 解析确认

文档解析与语义分析分别执行，界面展示各自状态：

- 题目、摘要、关键词；
- 学科和细分方向；
- 研究类型；
- 章节树；
- 研究问题和假设；
- 数据、样本和方法；
- 结果、结论和贡献主张；
- 表格、图片、公式、引文和参考文献。

用户重点确认学科方向、研究类型和章节完整性。低置信度解析明确提示，并允许重新解析或人工纠正关键元数据。

章节、正文、表格、图片、公式和引文位置属于文档结构；学科、研究类型、假设、方法及贡献等属于语义分析。人工纠正另存版本，不改写原始论文事实；受影响的语义分析和评判结果标记为需更新。

### 6.3 发起专业预审

解析完成后，中间聊天区显示摘要卡和当前所选标准、稿件类型。存在已发布的适用方案且类型已确认时允许“开始专业评审”，否则提示缺失项或必要确认。用户原先已明确要求评审且全部条件具备时可直接执行，不重复索要同一授权。评审任务固定本次论文、解析、语义产物、方案和期刊资料版本，按方案生成真实阶段；以下只是可选流程示例：

1. 研究设计识别；
2. 核心论点提取；
3. 领域评审；
4. 方法与研究设计评审；
5. 数据与统计评审；
6. 结果与证据评审；
7. 创新论证评审；
8. 可复现性评审；
9. 交叉质疑与证据验证；
10. 报告综合。

示例不是引擎固定流程，模块可按依赖串行或并行执行，也允许单模块方案。各阶段允许独立失败和重试，依赖未满足的阶段标记为阻塞。用户可以离开页面，稍后继续查看。报告生成有独立状态，失败时不重跑已完成评审。

### 6.4 查看问题与原文

评审意见在右侧论文中表现为真实批注：

- 问题文字下方绘制统一红线；
- 页边显示批注标记和连接线；
- 悬停红线显示简短意见；
- 点击红线后突出原句并展开侧边批注；
- 点击批注后将原文滚动到对应位置；
- 一句话存在多个问题时显示数量标记；
- 一个问题关联多个位置时支持在证据位置间切换。

所有红线保持一致，严重程度通过批注卡标签表达。“严重、主要、一般、建议”仅为候选显示标签，实际等级和含义由评判方案定义；未定义时不强制分级。缺失类问题定位到相关章节并展示检查范围，不伪造不存在的原句红线。

### 6.5 聊天与右侧联动

- 点击聊天中的原文引用，右侧切换到论文批注并定位；
- 点击右侧“询问 Copilot”，中间输入框自动带入问题上下文；
- 点击报告中的证据，右侧切回论文并定位；
- 查看证据后返回报告时，恢复原阅读位置；
- 切换项目或版本时，右侧恢复该对象上次查看的视图和位置。

### 6.6 评审报告

评审完成后，中间聊天区出现“评审报告已生成”产物卡。点击后右侧打开报告。

报告视觉版式尚未确定。内容基线见第 19 节；下列学术分析板块作为按研究类型选择的内容库，不作为所有稿件都必须具备的固定目录。报告首页先显示总体建议、主要理由、期刊匹配与可选评分，再展开这些板块：

1. 论文概述；
2. 总体评价；
3. 核心贡献判断；
4. 主要优点；
5. 关键缺陷；
6. 理论与研究假设；
7. 方法与研究设计；
8. 数据与统计；
9. 结果与证据；
10. 创新性论证；
11. 可复现性；
12. 写作与表达；
13. 可能的审稿人问题；
14. 修改优先级；
15. 系统无法确认的事项。

报告由 ReportTemplate 消费已保存的 ReviewResult 与 Finding 生成。模板声明需要的结果类型、字段、章节与呈现方式，并根据研究类型区分适用和不适用内容。正式判断可跳转到原文证据或缺失检查记录。

无论业务版式如何配置，系统保留论文版本、评审任务、方案版本、模板版本、生成时间和覆盖状态等溯源信息。报告区分“未发现问题、未检查、无法判断、不适用”，不把空白章节当作通过。缺少正式模板时只提供标明用途的结果预览，不宣称正式报告格式已经完成。

报告数据快照与 HTML、PDF、DOCX 等渲染产物分开管理；具体导出格式后续选定。重新渲染不覆盖旧报告，也不重复调用评判引擎。

### 6.7 上传修订版本

用户在聊天输入框拖入新文件时，系统检测当前项目已经存在论文，询问并默认作为新版本保存。系统结合内容哈希、段落映射和新版本复审结果进行问题匹配；有语义关系数据时可以辅助判断，输出：

- 已解决问题；
- 仍然存在的问题；
- 新发现的问题；
- 因上下文变化需要重新确认的问题。

首版采用完整复审后匹配问题。问题消失或原文被删除不自动等于“已解决”，需重新检查；无法匹配或证据不足时标记为需重新确认。后续在依赖覆盖可靠后增加增量复审，并保留完整复审入口。比较记录同时展示方案与模型版本，区分论文变化和评判配置变化。

### 6.8 删除项目

删除项目需要二次确认，删除范围包括：

- 全部论文版本；
- 原文件和解析产物；
- 向量索引；
- 评审任务和问题；
- 报告；
- Copilot 对话。

项目删除后立即撤销访问并停止相关任务，通过删除状态阻止迟到任务重新写入，后台跟踪各类数据的清理结果。匿名访问使用服务端签发的不可猜测会话凭证，workspace_id 仅为标识，不作为授权凭证。更换浏览器或清除会话后无法自动找回。在线数据、缓存、备份与供应商留存的实际清理边界须在部署时说明，不能把访问撤销等同于所有副本已物理删除。

## 7. Paper Audit Engine

### 7.1 文档结构层：Paper IR

PDF 和 DOCX 被转换为统一论文中间表示。核心对象包括：

- Document；
- Section；
- Paragraph；
- Sentence；
- Table；
- Figure；
- Equation；
- Citation；
- Reference。

每个可见元素包含解析产物内稳定的标识、文本或资源引用、语言、内容哈希、解析质量信息和适用的定位字段。PDF 优先使用页面坐标定位，DOCX 使用段落、句子和字符范围定位，不要求原生 DOCX 必须具备稳定页码。扫描件无法精确到句子时退化为段落或页面区域，并向用户说明定位精度。

每次重新解析生成独立 ParseArtifact，记录源文件哈希、解析器版本、结构 Schema 版本、覆盖范围和错误。标识不承诺跨修订或跨解析稳定；旧锚点绑定原解析产物，新旧元素通过显式映射关联。

### 7.2 语义分析层与论点证据关系

语义层消费指定 ParseArtifact，产出独立的 SemanticArtifact，包含 Claim、Method、Dataset、ResearchResult 等语义对象和来源锚点。模型推断不写回文档结构层。更换提取规则或模型时，只重建受影响的语义产物，不强制重新解析文件。

系统可以按评判需求提取以下关系：

- 研究问题由哪些假设展开；
- 假设由什么方法检验；
- 方法使用哪些数据和样本；
- 结果来自哪些表格、图片、公式或统计输出；
- 结论由哪些结果支持；
- 贡献主张依赖哪些结论；
- 摘要、正文和结论中的同一主张是否一致。

每条关系记录来源位置、提取方法和质量信息；低置信度关系不能单独支持严重问题。首版可用结构化对象与关系表存储，不要求图数据库或完整论点证据图。依赖图的模块需声明输入要求，输入不足时不得隐式当作完整图使用。

### 7.3 Review Pack

专业知识以版本化 Review Pack 组织，而不是只写入通用提示词：

```text
review-pack/
  manifest.yaml
  rubric.yaml
  methods/
  knowledge/
  prompts/
  schemas/
  tests/
  calibration.json
```

以上目录是建议组织方式，不强制首版具备全部内容。Review Pack 是规则、知识、模块配置及测试材料的版本化资源包；ReviewScheme（评判方案）是某次评审使用的执行配置，引用确切的 Pack 和模块版本，声明适用范围、检查项、依赖与结果 Schema。ReportTemplate 独立管理，不随规则包绑定固定报告版式。

Review Pack 可以按学科、研究类型和目标期刊组合，组合时显式处理规则重复、冲突和优先级，不自动相加权重。首版先实现框架与演示配置，正式规则确认后发布独立版本。

《生态学报》规则包参考并适配 nature-skills 中的审稿、统计和证据检查逻辑，作为本系统维护的独立配置发布。可增加供智能体读取的 SKILL.md 入口，但评分、状态和报告不依赖个人智能体的技能安装；适配范围与接入原则见第 20 节。

### 7.4 可配置评审模块与执行器

系统根据论文的学科和研究设计选择评审模块：

- 领域与理论评审；
- 方法和研究设计评审；
- 数据与统计评审；
- 论点与证据评审；
- 创新性论证评审；
- 可复现性与研究透明度评审；
- 学术表达评审。

上述模块是候选能力，不要求每篇论文全部执行。执行器读取方案形成无环依赖流程，模块声明输入类型、输出 Schema、依赖、允许的工具和资源预算。独立模块可并行，有依赖的模块按顺序执行；缺少输入、模块失败与不适用分别记录。

首版支持有限配置的受控流程，不建设任意代码插件平台。模块不得自行改变评判规则、增加工具权限或扩大数据访问范围。不同模块独立调用不等于其推理错误彼此独立，是否增加多角色由后续质量与成本评估决定。

### 7.5 验证机制与可选控辩审

所有正式结果均经过结构校验和适用的证据验证。需分开记录：

- 引用核验：原文、数字、位置是否对应；
- 规则核验：标准是否适用于该研究及当前输入；
- 推理核验：证据是否支持结论及严重程度。

验证结果记录方法、执行者或模型、时间和理由，不用单一 verified 状态暗示全部正确。未经校准的模型自报置信度不作为可靠概率展示。无法完成实质核验的判断应保留不确定状态。

方案可选择以下控辩审流程：

1. **审查者**提出问题和原文证据；
2. **辩护者**尝试使用论文其他内容反驳；
3. **验证器**核对引用、数字、位置和规则适用性。

最终裁决只能保留、修改、降级、标记不确定或删除候选问题。综合模型不能凭空创造新的事实性问题。

缺失类结果另外保存检查范围、检索记录、附件覆盖和解析完整性。即使定位到相关章节，也不代表已证明某事项在完整研究中不存在。

### 7.6 分层能力边界

架构支持接入论文内部有效性检查，包括方法是否能回答问题、结果是否支持结论以及论证是否前后一致；正式可用范围以已确认并通过验证的规则为准。未接入的能力显示未覆盖，不因模块名称存在而宣称已具备能力。

创新性分为内部贡献论证和外部文献比较。既没有外部检索，也没有可核验的用户提供比较材料时，只评价创新论证是否清楚，不能断言成果在真实学术世界中是否新颖。相关报告必须显示：

> 外部创新性尚未核验；当前意见仅评价论文内部的创新主张与论证。

接入外部比较后，每项结论限定于已检查的来源、时间和检索范围，记录全文或摘要访问层级，不将“未检索到”解释为“全球不存在”。目标期刊范围评价引用官方资料或用户提供的可追溯版本。外部资料通过受控检索适配层获取，视为不可信内容，不赋予 Copilot 任意联网权限。

### 7.7 评判结果、问题账本与报告服务

ReviewResult 是检查项级别的结构化结果，可表达优点、问题、评分或其他评价结论，并独立记录执行状态、判断状态和证据。Finding 是需要跟踪的问题对象，引用产生它的结果；它不承担所有评判数据的存储职责。

正式报告消费固定的结果快照及模板。总体评价、优点、评分和修改建议都需追溯到结果；问题状态在后续修订中改变时，旧报告保持不变。覆盖摘要由预期检查项与实际执行记录计算，不能只统计已有问题数量。

```text
论文源文件 → ParseArtifact（文档结构与原文定位）
                    ↓
            SemanticArtifact（按需提取语义）
                    ↓
ReviewScheme → ReviewRun → ReviewResult → Finding（需跟踪的问题）
                               ↓                 ↓
ReportTemplate ─────────────→ ReportSnapshot → 在线展示 / 导出
```

部分检查可直接读取文档结构，无需语义分析。报告以同一评审任务的完整结果快照为输入，Finding 只是其中的问题视图。

## 8. Copilot 设计

Copilot 是 Paper Audit Engine 的交互层，不是事实来源。它只能通过白名单工具访问当前项目：

- 获取项目和论文版本；
- 获取论文结构；
- 读取指定原文；
- 搜索论文；
- 获取问题和证据；
- 获取报告；
- 获取目标期刊资料与已登记的外部证据，按配置发起受控文献比较任务；
- 获取版本差异；
- 发起受控评审任务。

Copilot 不允许：

- 直接修改论文；
- 自主改变正式报告；
- 伪造不存在的原文；
- 将探索性回答伪装为已验证结论；
- 访问其他匿名项目；
- 使用任意终端、文件系统或互联网工具。

Hermes 可以作为首版 Copilot Runtime 接入，但必须位于适配层之后。Paper Audit Engine、项目数据和评审流程不能依赖 Hermes 私有状态，从而允许未来替换智能体运行时。

以下为逻辑契约示例，不是最终数据库 DDL，也不预先确定报告业务字段。各对象使用版本化 Schema；公共溯源、状态与关联字段保持稳定，学科特有内容放入有 Schema 约束的 payload，避免无约束自由 JSON。


```json
{

  "source_format": "docx",
  "source_file_key": "object_storage_key",

```

### 9.3 Finding

```json
{
  "id": "finding_id",
  "project_id": "project_id",
  "paper_version_id": "version_id",
  "review_run_id": "review_run_id",
```

Finding 是一次评审产生的问题实例；issue_thread_id 关联同一问题跨任务或跨论文版本的演变，不靠覆盖旧 Finding 保存新状态。严重程度允许为空，有配置时引用该方案的等级代码。证据验证明细保存在来源 ReviewResult 中。

### 9.4 EvidenceAnchor

```json
{
  "id": "anchor_id",
  "paper_version_id": "version_id",
  "parse_artifact_id": "parse_artifact_id",
  "element_id": "sentence_id",
  "locator_type": "pdf_region",
  "page": 12,
  "quote": "被批注的原文",
  "quote_hash": "sha256",
  "regions": [{"bbox": [112, 240, 486, 292], "coordinate_space": "page_points_top_left"}],
  "locator_quality": "exact"
}
```

以上为 PDF 示例；适配器统一坐标原点、单位与旋转处理。DOCX 锚点使用元素标识和字符范围，字符计数及文本归一化约定由 Schema 明确。跨行、跨页证据可关联多个锚点。文本哈希用于一致性校验，不用于证明判断成立。

### 9.5 ReviewRun

记录 paper_version_id、parse_artifact_id、可选 semantic_artifact_ids、scheme_id/version、journal_profile_id/version、article_type、review_scope、output_mode、用户附加关注、规则包与模块版本、模型与提示词版本、参数、状态、成本、耗时和错误。项目默认版本可以为空，启动时必须解析到确切的已发布版本并保存不可变快照，不能在执行中动态跟随“最新版”。

检查项执行记录保存 check_id、模块版本、输入摘要、依赖、attempt_id、重试次数和产物。发布结果时按任务和检查项保证幂等，重试不能产生重复正式问题。已完成任务不因配置变化被改写；重新评审生成新任务。报告生成另有独立任务状态。

### 9.6 ParseArtifact 与 SemanticArtifact

| 对象 | 必需的关系与信息 |
|---|---|
| ParseArtifact | 论文版本、源文件哈希、解析器版本、IR Schema 版本、状态、覆盖范围、结构产物位置 |
| SemanticArtifact | 来源解析产物、分析配置与模型版本、语义 Schema 版本、状态、来源锚点及语义对象 |

两类产物分开生成与版本化，已被评审引用的产物不得原地改写。PaperVersion 的 active_parse_artifact_id 只表示当前默认选择，不改变历史任务引用。

### 9.7 ReviewScheme

评判方案包含 scheme_id、version、适用范围、确切的 Review Pack 引用、check_id 列表、模块及其依赖、输入要求、输出 Schema、验证策略和执行预算。评分尺度、权重、严重程度映射均为可选配置。发布前检查依赖环、重复标识、Schema 兼容性和缺失资源；不兼容时拒绝启动并说明原因。

标准目录还保存 display_name、journal_profile_id、支持的稿件类型、输出模式、发布状态（draft／published／retired）和变更说明，供选择器读取。首个显示名称为“《生态学报》预审标准”。前端只负责选择和解释状态，实际方案兼容性及必查项由后端校验，不能由聊天模型临时创建“正式标准”。

### 9.8 ReviewResult

```json
{
  "id": "review_result_id",
  "review_run_id": "review_run_id",
  "check_id": "check_id",
  "criterion_id": "criterion_id",
  "schema_version": "1.0.0",
  "execution_status": "completed",
  "assessment_status": "issue_found",
  "observations": [
    {
      "id": "observation_id",
      "kind": "issue",
      "summary": "结论的适用范围超过已报告样本范围",
      "anchors": ["anchor_id_1", "anchor_id_2"],
      "verification": {
        "citation": "passed",
        "applicability": "passed",
        "reasoning": "uncertain"
      },
      "payload": {}
    }
  ],
  "score": null
}
```

执行状态区分 pending、running、completed、failed、blocked、cancelled、skipped；判断状态区分 issue_found、no_issue_found、unable_to_assess、not_applicable、not_checked。判断状态与执行状态分开，例如执行成功也可能无法判断。

observations 支持一个检查项返回多项意见，类型可为 issue、strength、assessment 等；Finding 引用具体来源结果及意见标识，source_result_ids 用于关联，具体映射另存。各维度验证记录还需附带方法、版本、理由与时间，上例仅展示状态摘要。示例中推理不确定的意见不能被报告表述为已验证缺陷。

评分仅在方案定义了尺度、依据及缺失项处理方式时产生。缺失类意见引用检查记录（范围、附件清单、解析覆盖、检索过程），不能仅靠空 anchors 表达“证明缺失”。

### 9.9 ReportTemplate 与 ReportSnapshot

ReportTemplate 包含 template_id、version、模板 Schema 版本、所需结果类型与字段、章节组织、适用条件、渲染配置和缺失数据策略。业务章节不作为全局固定字段写入评判引擎。

ReportSnapshot 包含 report_id、paper_version_id、review_run_id、结果快照标识、方案版本、模板版本、生成器版本、覆盖摘要、结构化报告数据及渲染产物引用。报告生成时校验结果与模板兼容性；缺少输入时显示未覆盖，或阻塞需要该输入的部分，不能隐式发起新的评审。

首版一份报告绑定一次评审任务。补充检查产生新任务时，显式记录来源与复用结果，仅复用论文、输入和规则兼容且可追溯的结果；合并成新的完整结果快照后再生成报告，避免混用不同版本结论。

### 9.10 JournalProfile、ExternalEvidence 与 OverallAssessment

JournalProfile 保存目标期刊标识、稿件类型、收录范围、排除事项、必要政策、来源 URL 或上传文件、资料日期和配置版本。官方明确要求与系统推断分开保存；近期文章可作为范围示例，不据此发明隐含录用规则。

ExternalEvidence 保存来源标识、标题、作者、发表日期、DOI/URL、取得时间、实际阅读层级（元数据／摘要／全文）、支持判断的位置与证据摘要。检索任务另存检索式、数据库或站点、时间范围、纳入理由和失败情况。论文内 EvidenceAnchor 不用于伪装外部证据；ReviewResult 通过 external_evidence_ids 引用。

OverallAssessment 属于评审结果快照，先于报告呈现生成，包含 recommendation（reject／major_revision／minor_revision／accept，或 null）、assessment_status（ready／provisional／needs_information）、decision_basis、目标期刊版本、规则版本、决定性结果引用、门槛状态、修订可行性、评分明细和覆盖率。暂无法判定时 recommendation 为 null；总体建议不是由报告模板临时决定。

评分明细保存 criterion_id、权重、适用状态、原始等级、折算得分、依据和扣分理由。权重、算分和门槛检查由程序完成，模型提供有证据的分项判断；不允许模型自由心算总分或将同一问题重复扣分。聚合结论只能引用已存在结果，不能新增事实性指控。

- PDF/Word 统一阅读器外观；

- 三栏可调整宽度布局；

### 10.2 后端

- FastAPI 作为业务与模型服务入口；
- PostgreSQL 保存项目、版本、配置、任务、评判结果、问题和报告元数据；

- 模型网关统一管理供应商、模型、重试、限流和成本。

### 10.3 文档处理

- DOCX 优先保留段落、样式、表格和字符范围；
- DOCX 结构化阅读与原始排版还原分别验收；如转换为 PDF 预览，单独保存转换版本及定位映射，不承诺与用户 Word 分页完全一致；
- PDF 使用学术文档解析器提取章节、参考文献和坐标；
- OCR 只对扫描或损坏区域启用；
- 所有解析器输出统一 Paper IR；
- 解析器放在适配层，允许替换或组合。

### 10.5 模块契约与替换边界

| 模块 | 输入 | 输出与责任边界 |
|---|---|---|
| 文档解析 | 源文件、解析配置 | ParseArtifact；不生成学术评判 |
| 语义分析 | 解析产物、分析配置 | SemanticArtifact；保留来源，不覆盖原文 |
| 评审编排 | 论文与产物引用、方案版本 | ReviewRun 和检查项记录；处理依赖、预算与重试 |
| 评审模块 | 声明的输入与规则配置 | ReviewResult；不直接修改报告或其他模块结果 |
| 验证模块 | 候选结果、原文及适用规则 | 分维度验证记录；不把引用匹配视为结论正确 |
| 问题账本 | 结果中的问题意见 | Finding 与跨版本关联；保留历史 |
| 报告服务 | 固定结果快照、模板版本 | ReportSnapshot 与渲染产物；不补造评判数据 |
| 总体评价聚合 | 分项结果、期刊配置、门槛与修订条件 | OverallAssessment；计算评分，给出可解释的系统审稿建议 |
| 外部证据服务 | 配置的来源范围、检索式或用户材料 | 期刊资料与文献证据；保留来源和覆盖限制 |
| Copilot | 用户请求、受授权项目上下文 | 解释或受控任务调用；不直接修改正式结论 |

这些是逻辑契约，不要求一一对应独立网络服务。接口以资源标识和版本传递依赖，避免依赖聊天历史、运行时私有内存或隐式“当前版本”。

## 11. 状态与错误处理

### 11.1 上传失败

保留项目和聊天，显示明确原因并允许重新上传。损坏文件、加密 PDF、超出大小和不支持格式分别提示。

### 11.2 解析不完整

允许部分成功。系统标出缺失页、乱码、公式、图表和 OCR 低置信度区域，不对缺失内容作确定性判断。

### 11.3 评审模块失败

其他模块继续完成。报告显示未覆盖模块，并提供单独重试。只有依赖失败模块的综合结论被阻塞。

### 11.4 证据失配

当原文引用无法通过 quote hash、位置或文本匹配验证时，候选意见不得进入正式报告，应转为待验证状态。

### 11.5 模型输出异常

结构化输出先通过 Schema 校验；失败后执行有限次数修复或重试。不得把未解析的自由文本直接保存为正式 Finding。

### 11.6 配置、模板与输入不兼容

缺少适用方案时停止专业评审并显示配置缺失；模板缺少输入时显示缺失字段或阻塞对应部分。规则、模块和结果 Schema 不兼容时在启动前拒绝执行，不静默降级为另一套标准。报告渲染失败可独立重试，不重跑评审。

### 11.7 取消、重试与并发

任务支持有限重试、取消、预算上限和幂等发布。阶段事件可在页面重连后恢复查询。用户切换论文后，后台任务仍引用启动时固定的输入；项目或工作区删除后，任务必须停止读写和发布结果。

## 12. 隐私与安全

- 文件上传前明确说明处理方式；
- 用户论文不得用于训练；上线前验证模型供应商的数据使用与留存配置，并明确告知实际处理边界；
- 匿名会话只能访问所属 workspace 的项目，所有 API、后台任务和文件下载都校验归属；workspace_id 与不可猜测文件键不能替代授权；
- 对象存储使用不可猜测的键和受控下载地址；
- 上传文档视为不可信输入，隔离解析进程；
- 文档中的提示注入内容不得改变系统规则或获得工具权限；
- Copilot 仅开放论文领域白名单工具；
- 删除项目时立即撤销访问，停止关联任务并清理原文件、派生文件、索引、报告和对话；
- 记录删除结果和失败重试，日志避免记录论文正文；部署前明确备份保留期、恢复时的删除重放和供应商留存处理，区分逻辑删除与物理清理完成。

## 13. 测试与评估

### 13.1 产品与交互测试

- 文件拖拽、上传和新版本识别；
- 标准预选、自然语言选择同步、稿件类型确认与缺失项追问；
- 切换标准只作用于新任务，标准升级不改变历史报告；
- 草案或未支持的稿件类型不能静默启动正式评分；
- 聊天到原文的双向定位；
- 批注与页面滚动同步；
- 报告与证据间往返后保持阅读位置；
- 项目切换时上下文隔离；
- 删除后的资源不可访问。

### 13.2 文档解析测试

- 单栏与双栏 PDF；
- 扫描 PDF；
- 中文、英文和中英混排；
- 含表格、公式、图片、脚注和参考文献的 DOCX；
- 页码、句子和坐标定位准确率。

### 13.3 评审质量测试

- 问题事实准确率；
- 专家问题召回率；
- 错误指控率；
- 证据定位准确率；
- 问题严重程度校准；
- 对优质论文与弱论文的区分度；
- 对反事实逻辑缺陷的敏感度；
- 不同学科、语言和研究类型的一致性。

### 13.4 回归集

每个 Review Pack 必须附带正例、反例、边界例和已知失败例。任何提示词、模型、规则或解析器升级都要重跑回归集，不允许只凭少量演示判断质量提升。

### 13.5 架构契约与替换测试

- 同一论文重复评审时产生独立任务，历史结果不会覆盖；
- 同一结果集套用不同模板生成报告，不调用评审模型；
- 模板缺少数据时明确标记，不能生成不存在的评分或事实；
- 高分不能覆盖已确认的否决条件；关键输入不足时能暂缓总体判定；
- N/A 与无法判断不混算，评分覆盖率、权重合计和算分正确；
- 无外部比较时不生成已核验创新性结论，范围不符与研究质量低分别记录；
- 更换语义分析配置无需重新解析文件；
- 更换评判方案无需修改文档解析器或工作台核心代码；
- 无问题、未检查、不适用、无法判断和模块失败能正确呈现；
- 重试不重复发布问题，项目删除后迟到任务不能写回；
- 不同解析版本的锚点不会串用，报告可追溯到实际使用的快照。

架构联调使用演示数据验证上述契约；专业质量验收使用正式规则和专家样本。两类结论分别报告，不以流程跑通代替评判质量合格。

## 15. 验收边界

### 15.1 架构与框架验收

评判标准和报告格式尚未确定时，可以先验收：

1. 作者无需登录即可建立、持续访问和删除项目；
2. 约定支持范围内的 PDF 与 DOCX 能转为统一论文结构，超出范围明确降级或报错；
3. 聊天区能够上传、显示进度、发起评审并打开产物；
4. 右侧能够在论文解析、论文批注和评审报告之间切换；
5. 样例意见能够定位到原文，缺失类意见能够展示检查范围；
6. 聊天、批注和报告引用同一评判结果与 Finding；
7. 论文、解析、语义产物、方案、任务、结果和报告具有明确版本关联；
8. 未配置并确认评分方案时不生成综合评分；使用通用方案时明确标识，不生成录用概率；
9. 所有无法核验的判断均被明确标记或排除；
10. 项目删除后所有业务数据均不可继续访问，后台不会重新写入；清理状态可追踪；
11. 替换报告模板无需重新评审，模板缺失输入时不补造内容；
12. 替换方案或模块配置无需重写工作台，重试与重复运行不会覆盖历史结果。

上述验收允许使用演示规则和模板，不代表专业评判首版已经完成。

### 15.2 专业评判首版验收

正式标准与报告格式确定后，额外验证：

1. 已明确支持的学科、研究类型、文件范围和能力边界；
2. 正式规则具备适用条件、依据、例外和回归样例；
3. 报告覆盖所需业务内容，结论、优点和评分均有来源；
4. 专家评估达到针对该范围事先约定的准确性、错误指控和重要问题召回门槛；
5. 修订复查能区分解决、延续、新增与不确定，不将匹配失败直接判为解决；
6. 成本、耗时和失败率在约定预算内，未覆盖能力可见；
7. 四档建议有决定性依据，证据不足可暂缓，分值不能抵消否决条件；
8. 期刊匹配和创新性评价能展示来源、比较范围和无法核验部分。

具体阈值在规则和使用场景明确后制定，本轮不虚构通用质量分数。

## 16. 实现难度与主要风险评估

### 16.1 总体判断

以下为基于本方案职责和范围的工程判断，尚未经过原型压测，不构成工期或质量保证。假设复用现成模型与文档解析能力、首批限制文档复杂度、采用模块化单体和后台 Worker，不自研基础模型、OCR 或 Word 排版引擎。

**总体架构可实现，基础框架难度中等；完整产品难度中高；跨学科、低误判的专业评判能力难度高，且有持续研究与校准的不确定性。** 标准和模板未定不阻碍基础框架，但会阻碍正式规则实现及专业质量验收。

### 16.2 模块难度

| 模块 | 难度 | 主要难点 | 首版控制方法 |
|---|---|---|---|
| 项目、版本与基础工作台 | 中 | 匿名会话持久化、状态恢复、数据隔离 | 明确单浏览器访问边界，使用统一授权校验 |
| 标准选择器与必要追问 | 低至中 | 选择状态、类型适配与任务快照一致 | 首版只提供《生态学报》，规则由后端校验 |
| 后台任务与评审编排 | 中 | 重试幂等、依赖失败、取消、成本预算 | 有限配置流程，先不做任意插件平台 |

### 16.3 最需要提前验证的风险

1. **定位可靠性：** 选取代表性的 PDF/DOCX，验证提取文本与实际显示位置一致，避免评审正确但批注错位。
2. **可配置边界：** 用两套有不同输出的演示方案和两种模板，证明更换配置不需要重写核心模块；仅做空接口不能证明可替换。
3. **结果可信度：** 正式规则确定后，分别测量引用正确、规则适用和判断正确，防止以引用匹配率替代专业准确性。
4. **单篇成本与耗时：** 按实际篇幅、模块数量、上下文读取量和重试情况计量；在测量前不给出固定低成本或短等待承诺。
5. **修订状态可信度：** 验证删除、改写、章节移动、解析失败等情况，不把“系统这次没找到”当作“作者已修复”。

### 16.4 实施建议与估算边界

保留三栏工作台和证据驱动方向，先完成可替换、可追溯的数据闭环。首版使用关系数据库存储语义关系，先做完整复审；微服务、图数据库、可视化规则编辑器和任意代码插件不作为前提。

当前没有团队配置、文档规模、并发量、供应商预算和正式规则复杂度，不能可靠承诺具体周数。实施前应分别估算框架工程、文档与定位适配、规则与报告接入、专家评估四部分；专家评估和规则修订时间不能仅按代码量折算。AI 编程辅助可以减少常规开发工作，但不能替代领域判断和质量验收。

## 18. 《生态学报》适配评判标准建议稿

### 18.1 标准来源与适用边界

首个目标期刊为《生态学报》中文版。本节提供一套可讨论、可执行化的评判标准，不声称获得该刊内部审稿表或编辑决策阈值。规则来源分为三类：期刊官方要求、研究方法依据、本系统拟定的评价准则。每条规则保留 source_type、来源和版本，不能混写为期刊官方标准。

该刊官方介绍强调生态学基础与应用研究的原创成果，也接收综述等类型；因此应先识别稿件类型，再选择检查项，不能用研究论文清单统一扣分。[《生态学报》关于本刊](https://www.ecologica.cn/stxb/ch/first_menu.aspx?parent_id=20080722101231001)

本轮检索日期为 2026-09-24，取得了官网页面的搜索索引内容，整页直接抓取未成功。期刊政策以下述官方页面为核对入口；正式发布规则包前，由人工或可用抓取渠道复核页面与附件，保存版本。未复核的动态细则不自动作为否决依据。

### 18.2 三层评判结构

1. **期刊适配与必要门槛：** 研究范围、稿件类型、核心科学有效性、必要伦理与投稿条件。单独输出，不由其他得分抵消。
2. **论文质量分项：** 对科学问题、创新性、理论、设计、数据、分析、解释、透明度和表达逐项评价，可选打分。
3. **总体审稿建议：** 结合门槛、关键缺陷、缺陷可修复性和评审覆盖，给出拒稿、大修、小修或录用建议。

单项问题严重程度、论文分数、总体建议是不同对象。一个问题的严重性取决于其对核心结论的影响，不按问题条数或修改字数决定大修、小修。作者身份、机构声望和资助金额不计入科学质量分数；期刊明确的投稿资格要求单独列为事务性检查。

### 18.3 期刊收录范围与必要门槛

| 检查项 | 本系统的判断方式 | 输出与处理 |
|---|---|---|
| 生态学主题匹配 | 说明研究对象、生态过程或格局、科学问题与目标读者如何对应期刊范围；不能只靠标题出现“生态”二字 | 匹配／边缘匹配／不匹配／信息不足，附官方范围与论文证据 |
| 稿件类型匹配 | 区分实证研究、模型方法、综述等，检查拟投栏目；文献计量与系统综述分别识别 | 类型适配及需要调整的栏目，不把栏目调整等同于科学性差 |
| 核心科学有效性 | 检查核心结论是否具备可成立的设计、数据和推理基础 | 存在已证实且无法合理修复的根本缺陷时可建议拒稿；缺少报告信息先要求补充 |
| 伦理与研究完整性 | 根据研究是否涉及动物、保护物种、野外采集、敏感地点或受访者等识别适用的许可、同意与声明要求 | 已满足／缺说明／需人工核实／不适用；不能从文风或异常数字直接推断造假 |
| 投稿材料与编辑规范 | 根据已复核的期刊指南检查语言、摘要、稿件类型、图表、参考文献、行号与其他必需材料 | 独立的投稿准备清单；可修正格式问题通常不构成学术拒稿依据 |

生态学主题匹配重点解释“研究回答了什么生态学问题”。区域制图、环境监测、指标评价、机器学习或管理案例均不能仅因采用这些形式而被排除；应判断是否产生有证据支持的生态认识。范围不符时可建议“对该刊拒稿／考虑转投”，同时保留其独立的科学质量评价。

官网投稿须知中可供核对的具体事项包括：中文稿件、研究论文详细英文摘要、摘要创新点、参考文献数量和全文行号；其中公布的英文摘要要求为不少于 500 词（综述除外），研究论文与综述参考文献数量要求分别为至少 30、50 篇。这些属于投稿准备检查，不作为科学创新性的代理指标。[《生态学报》投稿须知](https://www.ecologica.cn/stxb/site/menu/20080722101552001)

其他作者资格、署名、投稿操作和版式细则在发布期刊配置时逐条核对；正文无法提供的信息请作者确认，不从作者姓名、单位或文本风格猜测。期刊鼓励数据共享不等于所有数据均必须无条件公开，需区分敏感数据、许可限制和合理获取方式。

### 18.5 创新性怎样评价

创新性不能只检查作者是否写出“首次”“填补空白”，也不能将新地区、新年份、新软件自动等同于实质创新。建议拆成四个子项，候选满分合计 20 分：

| 子项 | 分值 | 判别依据 |
|---|---:|---|
| 贡献主张清楚 | 3 | 能明确指出新增知识或能力，而不是只列工作步骤 |
| 与最接近研究的比较充分 | 5 | 比较对象相关、引用可核验，明确已有研究已经做到什么 |
| 实质增量及生态学价值 | 7 | 是否揭示新机制、边界条件、方法能力，或提供有价值的新数据、重复验证、应用认识 |
| 新贡献有证据支持 | 5 | 核心结果、验证和不确定性足以支持所宣称的增量 |

文献比较表至少包含“本文主张—最接近研究—已有结论／方法—本文增量—支撑证据—剩余疑问”。按研究主题选取真正相关文献，不以引用数量、最新年份比例或只引用本刊代替判断。

最终创新性可以描述为：实质贡献明确、增量贡献明确、贡献有限、贡献尚未证实、无法判断。是否达到目标期刊要求需要结合完整规则和领域样例，不能由这些标签自动映射录用。

新地区可以用于检验理论的适用边界；长期监测、负结果和重复研究也可能有重要价值，不因“不是新算法”直接扣为零。反过来，模型复杂或使用热门技术，也不能代替生态学贡献。

没有外部比较材料时，只评价内部主张及其证据，不给完整 E02 得分；外部比较只读到摘要时，不据此声称已核实对方全部方法细节。报告明确检索日期、来源、检索范围和访问限制。

### 18.6 生态学研究专项检查

以下为拟议检查库，按研究设计和主张触发，不要求每篇论文全部具备，不预设统一最小样本量或一律要求多年数据。

| 检查方向 | 重点问题 | 判断边界 |
|---|---|---|
| 采样单位与独立重复 | 样地、样方、植株、土样或像元分别是什么单位；子样本是否被当作处理层面的独立重复 | 明确层级结构和推断对象，不能只按总观测数判断设计强弱 |
| 时间、空间与尺度 | 季节、年份、梯度、空间覆盖是否足以支持目标；分辨率和研究尺度是否匹配 | 单季数据不自动不合格，但不能无依据推断全年或长期变化 |
| 对照、混杂与因果 | 实验处理、参考区和基线如何设置；降水、海拔、土壤、土地利用等替代解释是否考虑 | 相关性和变量重要性不直接证明因果机制；观察性研究不一律要求操纵实验 |
| 物种与测量质量 | 物种鉴定、调查努力、检测概率、仪器与实验室测定是否适用且可比 | 按研究目标触发，不要求所有群落数据都采用同一种方法 |
| 数据预处理 | 缺失、异常、转换、尺度统一、重复记录和变量选择是否透明 | 需区分合理处理与可能改变结论的选择，不能从结果整齐直接认定不端 |
| 空间时间依赖与层级模型 | 分析是否处理相关结构、重复测量或分组；验证方案是否对应目标应用 | 是否需要分块验证由预测目标与依赖结构决定，不固定要求某一种模型 |
| 模型验证与数据泄漏 | 标准化、插补、特征选择是否仅利用训练信息；验证是否真正独立 | 必须根据论文可见流程判断，信息缺失时先询问，不能直接宣告泄漏 |
| 遥感、物种分布与生态服务模型 | 地面验证、样本偏倚、分辨率、参数来源、背景点和迁移适用性是否合理 | 使用某成熟模型本身不构成错误或创新，重点看假设与验证 |
| 不确定性与稳健性 | 效应大小、区间、模型误差、敏感性和关键假设是否足以支持主张 | 不按 p 值是否显著给质量分；没有显著差异不等于证明无效应 |
| 生态机制与管理外推 | 机制是否直接检验或仅属解释；管理建议是否限定区域、尺度和成本条件 | 不把局地关系推广为普遍机制，不要求所有描述研究都证明因果 |

时空结构数据的验证需结合预测用途，这一检查可参考 Roberts 等对结构化交叉验证的研究；它支持设置条件化规则，不支持“一律随机划分错误”这样的机械判定。[Cross-validation strategies for structured data](https://doi.org/10.1111/ecog.02881)

### 18.7 不同稿件类型的适配

| 研究类型 | 加强检查 | 避免套用的要求 |
|---|---|---|
| 野外操纵实验 | 处理分配、独立重复、对照、干扰与实验单位 | 不用子样本数量替代独立处理重复 |
| 观察调查与长期监测 | 采样代表性、时空结构、混杂、测量可比性与推断边界 | 不因未随机分配就否定全部研究价值 |
| 遥感、空间模型与机器学习 | 验证目标、时空划分、独立检验、误差传播、迁移与生态解释 | 不以模型复杂度代替创新性，不强制所有模型采用相同检验 |
| 系统综述与 Meta 分析 | 检索可复核、纳入排除、研究质量、效应量及非独立性、异质性 | 不要求作者产生新的野外样本 |
| 叙述性综述与理论研究 | 文献选择合理性、批判性综合、理论一致性、框架贡献与可检验命题 | 不强制效应量合并、统计显著性或实证假设格式 |
| 生态管理、政策与案例研究 | 案例选择、资料来源、分析链条、替代解释与适用条件 | 不一律要求实验设计；定性证据按适当标准评价 |

采用不同类型方案时，保存其明确权重；不把不适用的实验项直接记零，也不为了高分随意删除困难检查项。新增类型先定义规则和样例，再开放完整评分。

### 18.8 分项评分与缺失数据

候选子项采用 0—4 级评分锚点，再按子项满分折算：0＝已有证据表明不满足；1＝存在严重缺陷；2＝部分满足、需实质补强；3＝基本满足、有有限不足；4＝充分满足。不同维度必须补充具体正反例，不能只靠抽象标签打分。

子项得分＝子项满分 × 等级／4。程序汇总为分项与总分，保留内部精度，展示至多一位小数。分数反映本系统规则下的评价，不是统计概率。

- **无法判断／未检查：** 记 null，不作零分或满分。评审失败不能转成论文扣分。
- **不适用：** 依据预定研究类型规则排除并说明理由；归一化范围由方案确定，不能在看到得分后临时改变。
- **部分完成：** 展示“已评项得分／已评项满分”和加权覆盖率，不输出完整百分制总分，也不直接套用完整评分等级。
- **完整评分：** 所有适用计分项都有有效等级时，按适用满分归一为 100 分，附原始得分及方案版本；不同方案的总分不得直接排名。
- **门槛独立：** 范围、必要伦理、核心有效性及决定性不确定事项独立显示，不能被总分平均掉。

加权覆盖率＝已完成且可评分的适用子项满分之和／全部适用子项满分之和。无适用计分项时总分为空。总分不自动换算四档建议；如后续要设分数区间，须经专家样例校准，并保留门槛与可修复性优先的规则。

### 18.9 四档总体建议的判定

| 系统建议 | 核心条件 | 必须说明 |
|---|---|---|
| 拒稿 | 已确认不符合目标范围，或存在无法在合理修订内修复的根本科学缺陷，或有充分比较依据表明贡献达不到已配置要求 | 区分范围不符、贡献不足、设计／证据失效等原因；列决定性证据和为何不能通过修订解决 |
| 大修 | 研究有发表潜力，但需实质性重分析、补证、调整核心论证或重要方法说明，且存在合理修复路径 | 必须修改项、可选增强项、所需材料及复审通过条件 |
| 小修 | 核心设计、数据和结论已得到足够支持，剩余问题是局部澄清或编辑性修正，预计不改变主要结论 | 具体修改位置与完成标准；不能留下实质有效性问题 |
| 录用 | 已配置的必要条件满足，关键评价覆盖充分，没有未解决的阻碍发表问题 | 满足要求的主要依据、已核查范围和仍属于常规编辑处理的事项 |

这里的“录用”显示为“系统建议：录用”，不代表期刊承诺。缺少目标期刊时，建议标为基于通用方案；本项目默认目标为《生态学报》。

总体建议按“核实决定性门槛 → 评估核心质量与贡献 → 判断缺陷可修复性 → 检查覆盖与结论一致性”的顺序生成。确认范围不符可独立支持对该刊拒稿，无需为了凑齐分数执行全部检查；报告必须同时标明剩余未评项。缺乏资料本身不支持科学性拒稿。

关键材料不足且没有独立充分的结论依据时，recommendation 为空，显示“暂无法判定”，列出需要的材料；有局部依据但总体尚不充分时，只提供明确标记的暂定倾向，不能显示正式 ready 状态。录用建议要求关键门槛和必要评价均完成，不可由高分触发。

伦理或诚信疑点进入人工核实流程，报告描述可见事实，不自动认定抄袭、造假或违规。因报告缺项引起的疑问，与已有充分证据确认的重大问题分别处理。

### 18.10 可执行规则样例

**示例 A：E04-REP-01，独立重复与推断层级。** 输入为处理安排、实验单位、样本层级和分析模型；检查处理重复与统计推断是否一致。只有当论文明确将子样本当成独立处理重复，且该做法影响核心推断时，才提出实质问题。设计说明不足时先请求补充；建议修复可为明确设计、按真实层级重分析，若根本没有独立重复且因果结论依赖它，则标记为可能不可修复并人工复核。不能仅凭样本量较小触发。

**示例 B：E02-NOV-01，贡献增量比较。** 输入为论文贡献主张、结果和已核验的相关研究；输出逐项比较表及贡献等级。只有已读材料足以支持时才能说“该结论已被某研究报告”；检索不到反例只能描述已检索范围，不能判为世界首次。缺外部材料时对应子项为空。

**示例 C：E07-INF-01，因果与外推边界。** 输入为目标、设计、主要结果和结论；检查机制或区域推广主张是否超出识别与采样能力。解释性措辞清楚标为假设时不误报为确定性结论；修订可通过收缩主张或补充证据完成。是否大修取决于收缩后核心贡献能否成立，而非出现“影响”一词就触发。

上述样例还需领域专家提供正例、反例、边界例与合理修订答案，形成版本化回归集。先验证误判和漏检，再确定评分锚点与实际上线门槛。

## 19. 结构化评判报告内容建议

### 19.1 推荐阅读顺序

1. **总体建议：** 四档建议或暂无法判定、主要理由、论文与期刊配置版本、评审范围。
2. **期刊适配：** 收录范围、稿件类型、必要条件与投稿准备项；附具体来源。
3. **论文概述与主要优点：** 科学问题、方法、关键结果、贡献及有证据支持的长处。
4. **分项评价表：** E01—E09 的文字意见、适用状态、可选得分、证据和扣分理由。
5. **创新性专项评价：** 贡献主张、文献比较、实质增量、证据支持与未核实部分。
6. **关键问题与修改清单：** 按对结论的影响排序，区分必须修改和可选增强。
7. **次要问题与表达规范：** 局部表述、图表、单位、摘要与参考文献等。
8. **复审条件：** 哪些补充或修改足以消除当前障碍，哪些可能无法靠修改解决。
9. **局限与来源：** 解析缺失、未提供附件、无法访问的文献、未检查项及执行版本。

以上定义内容接口，视觉版式仍由 ReportTemplate 决定。用户可选择文字评价模式，或文字加分项评分模式；不允许只输出分数而缺少判断理由。

### 19.2 每条意见的最小内容

| 字段 | 要求 |
|---|---|
| 检查项与结论 | 使用明确 criterion_id，指出具体优点、缺陷或不确定事项 |
| 评判依据 | 区分期刊要求、方法依据与系统自拟规则 |
| 证据 | 原文锚点、外部证据或缺失检查记录；明确实际核验范围 |
| 影响 | 解释为何影响该问题的回答、核心结论或投稿适配 |
| 修改建议 | 具体可执行，避免“加强创新性”“完善讨论”等无落实对象的建议 |
| 必要性与优先级 | 必须修改或可选增强，说明是否影响总体建议 |
| 复查条件 | 给出解决标准，允许作者提供合理反驳或替代修复方案 |
| 状态与可选评分 | 已核验、需补材料等；分数仅在可评且配置启用时出现 |

### 19.3 总体意见的表达样例

以下仅为假设案例，用于说明报告写法，不是对任何实际论文的评价，也不是期刊决策预测：

> **系统建议：大修。** 研究主题与目标期刊方向匹配，现有数据有望回答所提出的生态学问题。主要障碍是样地内重复测量在当前分析中被按独立观测处理，以及结论将观察到的关联写成了已证实的因果机制。建议按采样层级重新分析，并据结果调整结论。若原始数据包含足够的独立样地，存在合理修复路径；否则需重新评估核心结论能否成立。外部创新性比较尚未完成，本次总体建议为暂定，不提供完整总分。

同一报告还应列出这两项问题各自的原文位置、方法依据与复查条件。拒稿理由必须对应决定性缺陷，小修不能附带必须重新开展核心实验的要求，录用不能同时保留未解决的重大问题。

### 19.4 参考来源与规则归属

- 《生态学报》的范围和投稿要求来自第 18.1、18.3 节链接的官方页面；正式启用前完成版本复核。
- 通用审稿维度可与 Nature 的审稿说明交叉检查，但其原创性与重要性要求不能直接移植为《生态学报》的门槛。[Nature：How to Write a Report](https://www.nature.com/nature/for-referees/how-to-write-a-report)
- 不同期刊的编辑定位不同，例如 PLOS One 明确强调技术严谨性而不以主观重要性作为同样的筛选门槛；因此期刊配置不能只改期刊名称。[PLOS One：Guidelines for Reviewers](https://journals.plos.org/plosone/s/reviewer-guidelines)
- 本文九项权重、评分锚点、四档建议逻辑和生态学检查库为本系统的设计建议，需由用户与领域专家确认并校准，不冒充上述期刊官方评分表。

### 20.5 接入关系与数据责任

```text
nature-skills 固定版本的相关指引
              ↓ 选取、核查、修改、记录来源
《生态学报》Review Pack + ReviewScheme
              ↓
可选 SKILL.md 入口 → 受控评审流程 / 智能体
              ↓
ReviewResult → Finding / OverallAssessment → ReportTemplate
```

适配后的 skill 负责说明检查方法、证据要求和工具使用方式；ReviewScheme 负责指定检查项、适用范围、预算和规则版本。模型提交结构化判断，后端执行 Schema 与证据校验、计算分数、校验门槛并保存结果。报告服务负责呈现固定结果，不让上游技能自行改动正式数据。

上游的 claim_pointer 和 evidence_pointer 转换为可核查的原文主张与 EvidenceAnchor／ExternalEvidence 引用；severity、blocking、resolution_test 映射为问题严重程度、是否阻碍当前结论及复查条件。没有可靠位置的意见保留待核验状态，不能为满足格式补造锚点。

规则来源记录至少包含上游仓库、提交、文件路径、实际依据来源、适配规则 ID、修改原因、修改版本和相关测试。单条规则修改不自动改变其他规则；发布新规则包版本后，经用户选择用于新的评审任务，历史结果不受影响。
